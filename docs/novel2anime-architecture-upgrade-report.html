1. 结论摘要

定性结论：LocalMiniDrama 适合作为主二开底座，但它现在更像“本地 AI 短剧工具集合 + 画布编排”。你的目标不是“小说专用工具”，而是“任意故事素材进来，自动跑完整 AI 漫剧流程”，所以改造重点应该放在多源故事素材导入、后端工作流、可恢复任务、剧本改编、QA 审计，而不是优先改 UI。

4. 故事素材入口

关键修正：进入系统的材料不应默认是小说。正确入口应叫 Source Intake / 故事素材导入。小说只是其中一种输入类型，系统要先识别素材类型，再决定后续走“改编、补全、结构化、分镜化”中的哪条路径。

支持的输入类型

输入类型例子进入系统后的处理方式是否需要编剧重改
小说 / 长文 网文章节、短篇故事、连载文本 章节拆分 → 摘要 → 事件图谱 → 短剧改编 需要
故事梗概 一句话创意、世界观设定、人物设定 扩写大纲 → 分集结构 → 剧本 需要
已有剧本 短剧剧本、对白稿、分场稿 结构解析 → 场景/角色/道具提取 → 分镜 通常只需润色
分镜表 镜号、画面、运镜、对白、时长 字段校验 → 美术 Bible 对齐 → 生图/生视频 不需要
漫画 / 图文稿 漫画页、条漫、图文脚本 画面解析 → 镜头重组 → 动画化提示词 部分需要
音频 / 视频转写 播客、口述故事、已有视频字幕 转写文本 → 情节抽取 → 剧本/分镜 通常需要

统一入口模型

source_intake
  ├─ classify_source_type      识别输入类型：novel / outline / script / storyboard / comic / transcript
  ├─ normalize_to_story_ir     转成统一故事中间表示 Story IR
  ├─ extract_entities          提取角色、场景、道具、时间线
  ├─ build_event_graph         构建事件图谱；已有分镜可跳过
  ├─ adapt_or_validate_script  需要改编则改编；已有剧本则校验和润色
  └─ handoff_to_pipeline       交给美术、动画、生成、合成、QA

为什么这对项目有益

避免产品被小说场景锁死

用户可能已经有剧本、分镜表、漫画、口述稿。系统如果只支持小说，会把高成熟度素材反而降级重写。

减少无意义 AI 改写

已有剧本不应再走小说改编；已有分镜不应再让编剧重写。多源入口能按素材成熟度选择最短路径。

更适合 LocalMiniDrama 现有能力

LocalMiniDrama 已有剧本、角色、场景、道具、分镜、视频合成。统一 Source Intake 能把不同输入接到这些现有模块。

后续扩展更稳

未来接漫画转视频、短视频二创、音频故事转漫剧，都可以复用同一套 Story IR 和工作流。

5. 核心制作岗位

岗位保留原则：本方案只保留动画制作链路中最关键的前 4 个岗位：导演、编剧、美术设计师、动画师。所有重叠职责必须做单一归属：一个任务只允许一个岗位负责，其他岗位只能消费其输出，不能重复生成或覆盖。

去重融合决策

重叠点最终保留负责人去除 / 合并对象原因
流程调度、预算、排期、最终验收 导演 去除独立制作人岗位 本地个人工具不需要单独制片层；导演兼任总控，减少审批链路。
剧情、人物动机、台词、旁白 编剧 导演不直接改写剧本；动画师不改剧情 故事内容必须集中在编剧，否则分镜和导演会把剧情改散。
镜头拆分、景别、运镜、动作、镜头内表情 动画师 编剧不写镜头；美术不管动作 镜头语言属于可执行生产层，应由动画师统一输出给生图/生视频。
角色外观、服装、发型、色彩、场景、道具 美术设计师 动画师不改外观；编剧不写视觉细节 视觉一致性必须有唯一来源，否则角色和场景会漂移。
图像提示词、视频提示词 动画师 去除独立 Image Prompt / Video Prompt 岗位 提示词是分镜执行产物；动画师根据美术 Bible 生成，不另设岗位。
特效效果，如雷电、爆炸、雨雪、能量波 动画师 去除独立特效师岗位 MVP 阶段特效写入 video_prompt；后期需要复杂 VFX 再拆。
QA 质量检查 系统门禁，不作为岗位 去除独立 QA 岗位 QA 应是自动审计规则，不能依赖主观岗位；导演只处理返工决策。
核心岗位 1

导演 / Director

负责项目目标、风格标准、流程总控、最终验收和返工决策。在系统里对应 Showrunner / Director Agent。

  • 确定项目类型、画幅、风格、目标时长。
  • 制定工作流计划和每个阶段的通过标准。
  • 决定哪些流程可自动跑，哪些节点必须人工确认。
  • 根据 QA 结果决定返工节点；不直接写剧本、不直接改分镜提示词。
核心岗位 2

编剧 / Script Writer

负责故事素材解析、事件图谱、短剧改编、人物性格、台词、旁白和每集钩子。在系统里对应 Source Analyst + Script Adapter。

  • 故事素材导入后保留原始内容与结构。
  • 抽取事件、人物关系、冲突、爽点和反转。
  • 把需要改编的素材改写成可拍摄的短剧剧本。
  • 输出对白、旁白、字幕初稿和分集结构；不写景别、运镜、镜头提示词。
核心岗位 3

美术设计师 / Art Designer

负责角色、场景、道具、色彩、灯光和视觉统一。在系统里对应 Art Bible Agent。

  • 生成角色视觉锚点、服装、发型和固定识别特征。
  • 生成场景空间结构、色彩、光线和环境氛围。
  • 生成关键道具设定和跨镜头连续性规则。
  • 为生图、生视频提供一致性约束；不定义动作、运镜和镜头内表演。
核心岗位 4

动画师 / Animator

在 AI 漫剧里不要求手绘逐帧，而是负责镜头拆分、动作设计、镜头内表情、运镜、首尾帧、图像提示词和图生视频提示词。在系统里对应 Storyboard / Motion Director。

  • 把剧本拆成可生成的镜头。
  • 定义每个镜头的动作、镜头内表情、景别和运镜。
  • 根据美术 Bible 输出首帧、尾帧、图像提示词和视频提示词。
  • 检查镜头之间的动作连续性；不改剧情、不改角色外观设定。

6. 多岗位互审机制

关键修正：重要节点不能由单个 Agent 一次性决定。编剧、美术设计师、动画师、导演必须形成“生成 → 质疑 → 修订 → 锁定”的互审流程。这里的“讨论”不是聊天，而是结构化审稿：每个岗位只审自己专业边界内的问题，并输出可执行修改意见。

互审原则

1. 产出者不做最终裁决

编剧写剧本，但不能自己判定“可拍”；动画师写分镜，但不能自己改剧情；美术定视觉，但不能改人物动机。

2. 审稿只审职责范围

动画师只审剧本的可镜头化问题；美术只审视觉一致性；导演只审整体节奏和返工优先级。

3. 争议由导演裁决

如果编剧想保留大段对白，动画师认为无法镜头化，导演根据节奏、成本和效果做最终决策。

4. 锁定后禁止跨层漂移

角色 Bible 锁定后，动画师只能引用不能重写；剧本锁定后，美术不能通过视觉设定改变剧情。

关键互审对

互审关系为什么需要审查问题输出
编剧 ↔ 动画师 剧本好不等于能拍；镜头好也不能破坏剧情 剧情是否能拆成明确镜头？动作是否支撑人物动机？对白是否太长？ 可拍性修订清单、镜头化建议、需要改写的台词/旁白
美术设计师 ↔ 动画师 动作设计必须服从角色和场景连续性 动作是否会破坏角色服装/道具？场景空间是否支持运镜？特效是否遮挡识别锚点？ 视觉约束补丁、镜头禁忌、参考图使用规则
编剧 ↔ 美术设计师 角色设定和世界观视觉必须服务剧情 视觉锚点是否体现角色性格？场景是否支撑情绪？道具是否有剧情功能？ 角色/场景/道具 Bible 修订意见
导演 ↔ 全部岗位 单点优化可能损害整体节奏、预算和成片效果 是否符合目标风格？节奏是否拖？生成成本是否过高？是否需要返工？ 通过 / 返工 / 降级 / 锁定决策

推荐工作流：结构化互审，而不是自由聊天

1. Source Intake
   输入故事素材，归一化为 Story IR。

2. 编剧生成 Script Draft
   输出事件图谱、分集剧本、对白、旁白。

3. 动画师审 Script Draft
   检查可镜头化、动作可执行性、对白长度、镜头密度。

4. 编剧按动画师意见修订 Script Locked
   锁定剧情、台词、旁白，不再被美术和动画随意改写。

5. 美术设计师生成 Art Bible
   输出角色、场景、道具、色彩、灯光、连续性规则。

6. 动画师审 Art Bible
   检查场景空间是否支持运镜，角色动作是否受服装/道具限制。

7. 动画师生成 Storyboard Draft
   输出镜号、景别、动作、运镜、首尾帧、图像/视频提示词。

8. 编剧审 Storyboard Draft
   检查是否偏离剧情、人物动机、关键台词和情绪节奏。

9. 美术审 Storyboard Draft
   检查视觉锚点、角色/场景/道具一致性。

10. 导演裁决并锁定 Production Plan
    通过后进入生图、生视频、配音、合成；不通过则指定返工节点。

13. 风险清单

高风险

大改前端而不改后端调度

会让 UI 看起来更完整，但流程仍然容易中断，无法一键生产。

高风险

直接接真实模型而无 Mock

成本高、回归难、问题不可复现。Provider 必须先有 mock。

中风险

继续把 Prompt 堆在单文件

短期快，长期不可维护。需要 Agent / Skill 化。

中风险

数据库只补列不建领域表

功能能跑，但故事事件图谱、工作流、QA 都会缺结构化支撑。
